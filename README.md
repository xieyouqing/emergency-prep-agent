# 灾害应急家庭准备 Agent

面向**老人与受教育程度较低者**的家庭应急助手：能问事、能自查、急事一键拨号。
单入口、按钮三选一、流程内不打字——目标是在最短路径上给出「本家庭适用清单 + 下一步只做一件事」。

> 状态：**V1.0 收尾中**（自查、日常问答、紧急三条链路已通；真机拨号/短信待验）。
> 详见 [`docs/07-V1.0-形态.md`](docs/07-V1.0-形态.md)。

## 三条链路

```
主页
├─ 问个事      日常问答：问句 → 答案 + 来源；查不到/涉及用药 → 转渠道
├─ 自查清单    14 项逐项三选一（有 / 没有 / 不确定）→ 分支页 → 结果页 + 下一步一件事
└─ 我现在有急事 紧急页：着火/被困 → 119，其余 → 120；两号并列，不做医疗判断
```

到期末尾还有一屏「顺手看一眼」（药品 / 食品饮水 / 医用材料 / 灭火器），判「该换新的」就进待采购。

## 快速开始

前端纯静态、零依赖零构建；后端只用 Python 标准库。

```bash
# 1) 前端（含 /ask 代理，改文件自动刷新）
node tools/dev-server.mjs 8000     # → http://localhost:8000/

# 2) 后端（日常问答）
python server/api.py 8001          # → http://127.0.0.1:8001/health

# 3) 测试（98 条）
node tools/checks.mjs              # 界面与状态机，74 条
node tools/checks-kb.mjs           # 知识库结构，8 条
node tools/checks-api.mjs          # 接口 + 前端接线，16 条（需后端在跑）
```

也可以直接双击 `src/index.html`（无自动刷新、日常问答需自行配置 `DAILY_API`）。

## 数据边界

- **清单条目**：安徽省《家庭应急物资储备建议清单（基础版）》14 项，皖应急函〔2024〕218号，2024-07-26。
- **交叉验证**：广东省疾控中心《家庭应急指南》2025-05-12；14 项中 11 项表述一致。
- **来源分级**：`official` / `consensus` / `cross-checked` / `inferred`。**知识库只收前三类，`inferred` 不入库**。
- **用户数据不出本机**：自查答案与家人号码只存 `localStorage`；日常问答只发送问题文本。

## 已知限制（如实列出）

1. **14 条自查判据里 10 条仍是 `inferred`**（我方推断，无权威条文）。界面上带「仅供参考」标记，不入知识库。
2. **目标用户可用性未验证**：验收 #2（未受训者 8 分钟拿到下一步）条件留空，校内无法取得「≥60 岁」样本，**不当作已通过**。
3. **真机未验**：`tel:`（安卓多为直接拨出）、`sms:`（iOS 对 `?body=` 支持不一）需真机确认。
4. **换机/清缓存即丢**：数据全在本机，不做迁移。
5. 知识库只覆盖「物品是什么、干什么用」，**没有场景应对与操作步骤**（燃气味、停电、灭火器怎么用等）。
6. 检索是**二字切片 + 口语别名**，不是向量检索；片段过百后需换检索器。

## 设计取向

- **简单优先**：零依赖、零构建、无用框架；一个文件一层职责。
- **来源优先**：能溯源才写进答案；不能溯源就不入库、不给「大概」答案。
- **诚实优先**：紧急页明说「手机能直接拨号就直接打，不用开这个」；测不到的东西宁可留空，不编数据。

## 迭代计划

### V1.1（收尾 V1.0 欠账）

1. **布局体现重心**：定位是「对话优先」，但主页主操作仍是「开始自查」，问答只在 chip 里。计划把「问个事」提为第一主操作，`自查清单` / `家人号码` 依次后排——否则入口与定位自相矛盾。
2. **返回文本改写**（见下节）：现在是原文片段直接当答案，答非所问且生硬。
3. **部署上云**：Nginx 托管静态目录，`/ask`、`/health` 反代到 `127.0.0.1:8001`，`systemd` 常驻 + 日志轮转。
   注意：**国内服务器 80/443 需备案**；无备案可用非常规端口或境外机器——部署前必须先定。
4. **真机验证三件**：`tel:`（安卓通常直接拨出，不弹确认，误触即真拨）、`sms:?body=`（iOS 支持不一致，可能需按 UA 改用 `&body=`）、5 秒撤销计时；另需在真机系统字体放大下复验布局。
5. **交付前两个必答**：
   - 验收 #1 要求「按家庭结构 / 灾种裁剪」，但契约写的是「筛选暂不做」——两处矛盾，需定夺：降级验收口径或在基线注明延期。
   - 10 条 `inferred` 判据需要补权威来源，或明确标注推断并给出验证路径。

### V1.2（内容与检索）

1. **知识库扩库**：现在只覆盖「物品是什么、干什么用」，缺**场景应对**（燃气味、停电、停水、火灾初期、地震躲避、洪水撤离、被困）与**操作步骤**（灭火器怎么用、防火毯怎么盖、面罩怎么戴）。优先级：燃气/停电/停水 → 火灾初期与器材用法 → 地震/洪水。
2. **返回文本结构化**：`answer`（一句直接回答，属于我方改写）+ `quote`（支撑该句的原文）+ `sources`（出处）三段分离，前端分别展示。
3. **20 条评测集**：问题 × 期望来源片段，门槛「命中率 ≥ 80% 且无来源回答数 = 0」。**评测集先于检索器升级**——没有它无法证明换法更好。
4. **检索器升级**：片段过百后从「二字切片 + 别名」换成向量或 FTS5 分词方案，接口不变。

### V1.3（生成与个性化）

1. **RAG 的 G（生成）**：触发条件——需要跨多段综合、片段过长需摘要、检索命中但原文读不懂。开启时必配：prompt 只依据给定片段、逐句标引用、**后置校验**（每句能映射回片段，映射不上整段丢弃）、校验不过降级为返回原文。
2. **裁剪三维**：按灾种 / 家庭结构（有老人、有婴儿）/ 居住形态（高层、低层）筛条目，配 ≤3 选项、不打字。
3. **动作库**：仅收 ≥2 个权威来源表述一致的动作，有分歧转渠道。

### 长期（工程与质量）

多窗口协作（预演流程见 `AGENTS.md` §6）、XSS 防御（数据一旦外部化即成注入面）、dev-server 加固（畸形 URI / 路径前缀）、跨设备数据迁移（6 位迁移码）、真实目标用户可用性测试。

## 关于「返回文本」的问题与改法

**现状**：命中后直接把知识库片段当答案。片段是清单原文（「……用于待救援及避险期间生存需求」），于是：

- 问「水要备多少」，返回的是「饮用水属于什么」，**没答「多少」**
- 句子从清单里截出来，读着像说明书，不像回答
- 段落一长，手机上要读三行以上

**改法（V1.1 做，不依赖模型）**：每段知识库加一个 `answer` 字段——**一句人话直接回答**（如「每人每天 1 升，备足 3 天」），同时保留 `quote`（支撑这句的原文）与 `sources`。

- 检索命中 → 显示 `answer`，下面附原文与来源
- `answer` 属于**我方改写**，必须与 `quote` 语义一致；改写得失真的，降级显示原文
- 这样既解答问题，又不牺牲溯源：评审能看到「这句是从哪段原文推出来的」

**不做**：不在 V1.1 引入模型生成（会改写内容、增加溯源难度，见 V1.3 的约束）。
