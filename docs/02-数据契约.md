# 02-数据契约 — 数据契约（T1）

> 这是 T2–T4 的**共享约定**。后面几个任务只引用这里，不各自定义字段。
> 依据：`任务说明` v1.2 §2（三分支）、§3（条目与判据）、§6（验收 1–4）。

## 1. 条目 Item

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 稳定标识，一经发布**不复用** |
| `name` | string | 给用户看的名字，短句 |
| `check` | string | 10 秒判据，一句；给不出判据的条目**不入清单**（§4） |
| `checkSource` | string | 判据出处：cross-checked 及以上写原文摘录与抓取日；inferred 写「我方推断，无外部依据」 |
| `checkLevel` | string | `official` / `consensus` / `cross-checked` / `inferred`（见 `04-数据来源.md` §0） |
| `howto` | string｜预留 | **分支页的操作指引**（怎么摇、在哪看）。现在全部留空，界面按「有则显示、无则兜底」。属内容资产，需来源，与 T9 判据一起补 |
| `source` | string | 回指省级清单的条目编号或名称（§6 验收第 1 条） |
| `scope` | string[] | 适用灾种：`['fire']`／`['flood']`／`[]` 表示全灾种 |

**暂不做**：家庭结构、预算这两维裁剪字段 —— 等 14 项清单落地（T5 之后）再补，避免现在定错。

## 2. 答案

```
type Answer = 'yes' | 'no' | 'unsure'

answers: Record<itemId, Answer>   // 没答的项＝键不存在，不是 'unsure'
needsHelp: string[]               // 用户走了「找人帮」的 itemId
```

**关键区分**：`unsure` 表示「不确定」，**不等于**「确认没有」。只有 `no` 才进待采购。
`needsHelp` 单独记，不能把它压成 `unsure` —— 否则结果页和转发消息都丢了「需要别人帮」这个信息。

## 3. 三条分支的去向（§2）

| 入口 | 走法 | 落到哪 |
|---|---|---|
| 10 秒可验证 | 给 `check` 判据，用户自己看 | 回链路，重答为 `yes` / `no` |
| 无法验证 | 转「找人帮」 | `needsHelp` 加上该项 |
| 确认没有 | 直接认 | `no`，进待采购 |

三条都必须有出口：不允许「无路可走」，也不允许「回到同一屏」循环（§6 验收第 4 条）。

## 4. 结果页分组规则

| 分组 | 取哪些 | 下一步该给什么 |
|---|---|---|
| 已有 | `answers[id] === 'yes'` | — |
| 待采购 | `answers[id] === 'no'` | 今天把 X 配上 |
| **找人帮** | `id ∈ needsHelp` | 发消息请家人帮你看 X（T7） |
| **待确认** | `answers[id] === 'unsure'` 且 `id ∉ needsHelp` | 先确认 X 有没有：<check> |

**为什么要拆开**：用户选「找人帮」是**已经决定要人帮**，再让他「先确认一遍」等于把活退回去；只有「单纯不确定、还没决定找谁」才该给判据让他自己看。

**「待确认」的产生条件（2026-11-04 补）**：正常流程里「不确定」→ 分支页必然当场产生去向，所以待确认为空。它靠 **T11 主动退出**产生：退出时未走完一轮，**只把当前项**记 `unsure`，其余未答保持未答。剩余未答不冒充待确认。

**下一步只出一件**（顺序固定）：
1. 有「待采购」→「今天把『X』配上」
2. 否则有「找人帮」→「发消息请家人帮你看『X』」
3. 否则有「待确认」→「先确认『X』有没有：<check>」
4. 否则 →「都配齐了，半年后再看一遍」

## 5. 持久化

- key：`ep-v1`；值：`{ answers, needsHelp, lastCompletedAt }`
- `lastCompletedAt`：走完一轮时写入（供 §2 触发时机：无记录 → 首次自查；≥ 90 天 → 顶部提示）
- 结构变更时**换 key 前缀**，不做数据迁移（§8 已知缺口：换机/清缓存即丢）

## 6. 两条用例（T2 用它验收）

**用例 A —— 全「有」**

输入：5 项全答 `yes`，`needsHelp` 为空
预期：已有 5 项；待采购 0；待确认 0；下一步＝「都配齐了，半年后再看一遍」

**用例 B —— 全「不确定」且全选「找人帮」**

输入：5 项全答 `unsure`，`needsHelp` 含全部 5 项
预期：待确认/找人帮 5 项；待采购 0；下一步＝「先确认『手电（可手摇充电）』有没有：按一下开关能亮；摇 30 秒还能亮」；**不能**出现「今天把『手电』配上」

## 7. 审查后补的四条

1. **中断继续**：启动时若 `answers` 非空且没走完，从**第一个未答项**继续，不重来。全部答过＝直接进结果页。
2. **撤销语义**：撤销一项＝删掉 `answers[id]` 键 ＋ 从 `needsHelp` 移除该 id，回到「未答」；**不写回「否」**。
3. **零条目兜底**：`ITEMS` 为空或加载失败 → 显示「清单暂时打不开，请稍后再试」，不进入结果判定，不显示「都配齐了」。
4. **筛选暂不做**：`scope` 只作标注，T2–T4 不做灾种筛选；筛选等 14 项清单落地后单独开任务。
